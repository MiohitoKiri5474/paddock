# paddock design

Agreed on 2026-10-19 in a design interview. Vocabulary is defined in [CONTEXT.md](../CONTEXT.md); decisions with lasting trade-offs are recorded in [docs/adr/](adr/).

## Purpose

paddock replaces herdr for one person on one Mac (or Linux machine). It is a terminal workspace (spaces, tabs, splits) whose terminals keep running when paddock closes, and it tracks coding agents' sessions (Claude Code so far) and the branches they and their subagents work on, so you can see at a glance which ones need you.

Not in scope for now: remote machines, and a scripting API beyond `paddock worktree` (see Worktree command).

## Architecture

- **One binary, its own server** ([ADR 0003](adr/0003-no-daemon-single-instance.md), [ADR 0007](adr/0007-native-backend-with-a-server.md)). `paddock` opens the app, one at a time. The same binary, as `paddock server`, is the server that hosts the terminals: the first paddock that needs it starts it in the background, and it ends with its last terminal. No other daemon: while the app is closed, only that server (the hidden tmux server instead, on the legacy tmux backend) and the agents' hooks run.
- **Native server, the backend** ([ADR 0007](adr/0007-native-backend-with-a-server.md), [ADR 0008](adr/0008-layout-saved-and-restored.md)). Since ticket 45, `[backend] kind` defaults to `"native"`: paddock's own server (`paddock server`) hosts every space, tab, split and float, keeps each terminal's emulator, and saves its layout to `layout.json`; see *Native server* and *Native layout* under Backend seam. The tmux backend below is the legacy option, chosen with `kind = "tmux"` and kept until v0.2; the text that follows describes tmux where the native server copies its behaviour.
  - *Old tmux server:* tmux's terminals are not migrated. At start on the native backend, paddock asks `tmux -L <socket> display-message -p '#{pid} #{start_time}'` (`backend::OldTmuxServer`; never a command that starts a server; no tmux, no server, or no answer within 1 s is silence). If a server answers that it has not told about, paddock says its terminals are not moved here and to close it with `tmux -L <socket> kill-server`: first in the tab bar at start, and printed however `app::run` ends (on leaving, or on an error at start such as a declined restart). Only once printed is the server remembered as told, by that pid and start time, in `old-tmux-server` in the state directory: the same server stays quiet at the next start, a new one (closed and started again) is said again, and a start killed before printing says it again next time.
- **Hidden tmux server, legacy** ([ADR 0001](adr/0001-tmux-as-hidden-backend.md)). `tmux -L paddock`, started with paddock's own minimal config (`escape-time 0`, `extended-keys on`, no status line, no prefix) and a clean environment (`SUPACODE_*`, `TERM_PROGRAM` and similar variables removed). The user's own tmux is never touched. Each space is a tmux session, its tabs the session's windows and its splits their panes ([ADR 0006](adr/0006-sidebar-items-are-tmux-sessions.md)), so `tmux -L paddock attach` shows the same structure. Floats are windows of the session too, marked as not being tabs, so `tmux attach` shows them as well.
- **Own renderer** ([ADR 0002](adr/0002-own-renderer-via-control-mode.md)). paddock is a client of its server, one connection per space (on the tmux backend, a tmux control-mode client per space). Each terminal's raw output feeds its own terminal-emulator instance in the app; paddock draws everything with ratatui and keeps scrollback, selection and search itself. Spike 0a picks the emulator crate. Written in Rust.
- **Backend seam.** The app, the CLI and the hooks reach the backend (the native server, or tmux) only through `src/backend/`, the backend interface of [ADR 0007](adr/0007-native-backend-with-a-server.md). `backend::Backend` does what paddock asks of the process that hosts its terminals: spaces, tabs, splits, floats, zoom, resizing (by key, or by dragging a `backend::Border` it found with `border_at` through `drag_border`), roots, and queries such as a terminal's directory, foreground command and shell pid. `Backend::attach` opens a space's `Connection` (input, sizes, detach), and the connection reports `backend::Event`s: output, a changed structure, spaces made or ended, and its end. What a space holds is `backend::Structure`: its tabs and their splits, and its floats, which are never tabs. Spaces, tabs, floats and terminals are `SpaceId`, `TabId`, `FloatId` and `TerminalId`, made only by the backend, each its own type. `backend::hook_terminal` reads which of paddock's terminals a process (a hook, `paddock worktree`) runs in, and the instance id that names that backend's hook event log, from its environment (an empty variable counts as unset), as a `backend::Instance` (the backend's kind and its id, which together name the log). A set `TMUX` decides: tmux's `TMUX_PANE`, believed only when `TMUX` names paddock's socket, else an external session (a tmux of the user's, even one started in a native terminal, whose `PADDOCK_*` it passed on). Else the native server's `PADDOCK_PANE` (`%N`), `PADDOCK_SOCKET` and `PADDOCK_INSTANCE` (plain digits, above 0), believed only when `PADDOCK_SOCKET` is the server socket under paddock's own state directory (as written, else with the directories' symlinks resolved, so `/var` and `/private/var` match), and not when `STY` or `ZELLIJ` says the process runs in GNU screen or zellij started there. Native terminals never have `TMUX` (their environment is clean), so there the native variables come first. Not caught: an editor or another terminal app started from a native terminal, whose own terminals pass `PADDOCK_*` on; their agents are recorded in that native terminal. It is the one place that reads these variables.
  - *Attach contract:* `attach` gives, for each terminal, a `Replay`: one byte stream that, fed to a fresh emulator of the terminal's size, rebuilds its screen, scrollback, cursor and modes (keyboard, mouse, bracketed paste, the alternate screen). Output that follows continues the same stream, so nothing between the replay and the first output is lost or shown twice. tmux builds it from `capture-pane` and `display-message`; a backend with its own emulator sends its snapshot.
  - *Debug state:* `paddock debug state --json` (`src/debug.rs`, left out of `paddock help`) prints the backend's state as one JSON object, read through `Backend` alone: `spaces`, `structure`, `root`, `instance` and `terminal_details`, which gives every terminal's directory, foreground command, shell pid, tty, scrollback length and the variables a hook in it sees (`hook_env`, what `hook_terminal` reads back). It holds `version` (1; it changes when a field changes meaning or goes away), the backend's `instance` (`null` when none runs), the path of its hook event log (`event_log`, `null` likewise), and the spaces oldest first, each with its id, name, root and current tab, its tabs (name, whether the name is automatic, zoom, splits) and its floats (key, splits); a split is a terminal with its place, size and focus, plus those details. It never starts the backend. The test harness reads state through it (see Testing).
  - tmux's commands, formats, notifications, environment variables, control mode and replay live in `src/backend/tmux/`, private to the backend. Ids keep tmux's spelling (`$N`, `@N`, `%N`) as text only where they are stored or come from hooks: `layout.toml`, the hook event log, and the sessions and their rows (which also carry external sessions' keys). A second backend fills in `Backend`, `Connection` and `hook_terminal` without touching their callers: `Backend` and `Connection` are enums over the two, picked by `[backend] kind` (`config::BackendKind`; `Backend::configured` reads only that setting, for `paddock debug state` and `paddock worktree`).
  - *Native server* (`src/backend/native/`, the default `[backend] kind = "native"`; tickets 40-45). `paddock server` (left out of `paddock help`) is started in the background by the first paddock that makes a space while none runs (or, at its start, finds a saved layout) (`setsid`, the clean environment of `backend::env`, its output in `server.log`). It listens on `server.sock` in the state directory, mode 0600; a socket path longer than the platform takes (103 bytes on macOS, 107 on Linux) is an error that says to shorten `XDG_STATE_HOME`. One server per user: it holds an exclusive `flock` on `server.lock` (with its pid); a second one waits up to 3 s for the lock (an ending server lets it go), then exits without serving. It ends when its last terminal ends (hanging up every shell and removing its socket), on SIGTERM, SIGINT or SIGHUP, and 15 s after it started if no terminal ever came. Its instance id, which names its hook event log, is a random non-zero `u32` (`arc4random`; `getrandom` on Linux) drawn each start and sent in its hello, so no earlier server's log (whose records name that server's terminals, and to which an agent that outlived it may still write) is read by a new one, but by a one in four billion chance. Its log is `events/native-<id>.jsonl`, apart from tmux's `events/<pid>.jsonl`, so a tmux server whose pid equals a native server's id never replays it, nor the other way round (a tmux server that reuses an earlier tmux server's pid still reads that one's log, as before). It hosts every space, each with its tabs and splits (ticket 41) and its floats (ticket 42): each terminal is a login shell (`-zsh`, as tmux starts it; a float's program runs as `$SHELL -c <command>`, not a login shell, as tmux runs a window's command) on its own PTY, with the clean environment plus `COLORTERM=truecolor`, `AGY_CLI_OSC7501=on` and its hook variables (`native::hook`): `PADDOCK_PANE` (its terminal id), `PADDOCK_SOCKET` (the server's socket path) and `PADDOCK_INSTANCE` (the server's instance id), which `paddock debug state` reports as its `hook_env` (rebuilt from the server's socket and id, not stored); and an alacritty_terminal emulator (`Emulator::answering`) that answers DA and `CSI ? u` for the program; XTVERSION (`CSI > q`) gets `paddock <version>`. A terminal's directory and command come from the PTY's foreground process group, through `native/proc.rs`, the one place that differs by platform: macOS `libproc`, Linux `/proc/<pid>/cwd` and `/proc/<pid>/comm` (a command name the kernel cuts to 15 bytes); agents are matched to terminals (the `claude agents --json` snapshot, by walking `ps` parents up to a terminal's shell) through `Backend::terminal_pids`, and the foreground-command poll of an Antigravity session through `Backend::terminal_commands`, which the server answers from its terminals. Antigravity's status reports (OSC 7501) are read from the output the server streams, as from tmux's. Spaces are listed oldest first; a name another space has is refused in tmux's words (`duplicate session: <name>`), which paddock shows. Closing a space takes it out at once, as `kill-session` does (its client gets `Ended`, every client `SpacesChanged`), then hangs up its shells; closing the last space ends the server once it has answered, as its last terminal ending does, not waiting for a shell that ignores the hangup. A program once reaped is never signalled again, as its pid may be another process's. A float is one terminal on its key, never a tab, at most one per key in a space (a second is refused): it starts at the space's size until the client sizes it to its box (`Request::ResizeFloat`, sent on the attached connection), apart from the tabs, whose layout never touches it. It closes as soon as its program exits and is reaped, so its key takes a new float while its last output is still read, and with its space, which ends when its last tab closes, hanging its floats up. `Structure::floats` shows each with its one terminal filling it; `float_active` stays false, as the server never makes a float a page. It saves its layout and rebuilds it when it next starts (ticket 44, see *Native layout*); the app starts it at launch when `layout.json` is there, so the spaces in it come back (`paddock worktree` and `paddock debug state` never start it for that).
  - *Native layout* (`native/layout.rs`, `native/tab.rs`, `native/space.rs`). The server keeps each tab's splits as paddock's own tree: a terminal, or a row (side by side) or column of cells with one cell of border between neighbours, each cell with its share of the row (its weight). Laid out at the space's size, the tree gives each terminal its place, and the server sizes its PTY to it; a space resized keeps each cell's share, at least one cell each. A tab smaller than its smallest layout (one cell per terminal plus the borders) is laid out at that smallest size, and the client draws what fits: no terminal ever gets no cell. Every change first makes the weights the sizes drawn at that moment (except that `=` and a closed terminal leave a row too small to give each cell its share with its weights, so the shares come back when the tab grows again; a split, the resize keys and a drag take the sizes drawn there, so they move what is drawn), then works in cells, as tmux does, so the sizes match tmux's to the cell: a split takes the second half (`(size - 1) / 2`) and the focus, into the same row when it runs the same way; a closed cell's place goes to the cell before it (after it, for the first), a row left with one cell gives way to it (joining the row around it if that runs the same way), and the terminal focused before it takes the focus; `C-a H/J/K/L` move the border after the focused cell in its nearest row or column (before it, for the last), down to one cell, without an error; `=` evens out the nearest row or column where that changes what is drawn (not one already even, nor one a smallest size inside it holds), the first cells taking what is left over; focus by direction goes across the border to the overlapping terminal focused last, from the other edge past the tab's; a zoomed terminal fills the tab while the others keep their places (and sizes), and anything that changes the layout or focuses another terminal gives the zoom up. A border found under the mouse (`BorderAt`, a `BorderHit`) is moved by sizing the cell before it (`DragBorder`, at most one every 40 ms as on tmux, all of a drag on one connection the client keeps for drags), named by its last terminal (climbing from it to the first row where its cell is not the last finds that cell), so every border can be dragged, also beside a nested row. Closing the current tab goes back to the tab current before it, else to the one before it. The structure (tabs, floats, names, places, focus, zoom) is the server's; whenever it changes the client attached to that space gets `Notice::Changed` (`Event::Changed`) and reads it again (`Request::Structure`), as tmux's notifications made it do; a request that fails or changes nothing sends none, and one that changes a tab sizes only that tab's PTYs. `paddock debug state` reads the same structure, so its sizes are what is drawn. Tabs not renamed are named every 300 ms after their focused terminal, as paddock's tmux config names them: a shell (`-?(ba|z|fi|da|k|tc|c)?sh`) after its directory's last part (`/` for the root), anything else after its command, both read (`native/proc.rs`) from the PTY's foreground process group; a renamed tab keeps its name. The server saves the layout to `layout.json` in the state directory (`native/saved.rs`, ADR 0008): spaces in order with their names, roots, sizes and current tab, each tab's name (and whether it is automatic), focus, zoom and tree with its shares, each terminal by its directory (read with `native/proc.rs`, the space's root while it cannot be read) and the agent session last seen in it (`agent`: its kind, session id, and whether its conversation is `over`; left out for none), and the space paddock shows (`Request::SetCurrent`, which takes over `layout.toml`'s on native; the sidebar width stays there). It looks every 100 ms and writes only a change, at most once every 250 ms: the layout is taken with the state locked, the directories read and the file written (a temp file, mode 0600, synced, then renamed over the old one, and the directory synced) after, except the last, as the server ends. A server that ends writes it at once and no more, so the shells it hangs up leave it whole, and a server left with no space removes it. Floats are left out: their keys make them again when wanted. The sessions come from the server's own hook event log (`native/seen.rs`), which it reads as hooks add to it, every 100 ms and once more as it ends, before it hangs up the shells; a terminal closed is forgotten. A terminal with no session takes the first one a record names; after that only a `SessionStart` puts another in its place, as the old session's records (its `/clear` end, a late `Stop`) may land after the new one's start, each hook being a process of its own. Antigravity sends no `SessionEnd` (`AgentKind::reports_end`): its session is over once its terminal is seen back at a shell at a save (its foreground process group's name is a shell's, as `Sessions::end_exited` tells one; an unreadable one changes nothing), but only after a record of it came from that terminal, so a session a restore seeded is not over before its resume runs. agy ships as a native binary (`~/.local/bin/agy`, from its install script), so its process is named `agy`: the same process group in the foreground again (`fg` after `C-z`; not a fresh agy, which another group runs), or any record of the session, takes that end back; another program there (an editor after agy quit) does not. A resumed agy that never sends a record (not installed, or the session not found) is never seen to end, so it is resumed again at every restart, as is any kind's resume that never reports. A `SessionEnd` (any reason, `/clear` too) makes the conversation *over* (the saved flag, not the dashboard's *ended*, which `/clear` is not), and only its own `SessionStart` again (a resume in the same terminal) takes that back, not a hook landing late. A reboot signals the agents and the server at about the same time, so Claude may log its end first: at the last save, as the server ends, an end from outside logged less than 2 s before the server began to close, or after, does not make the session over, even if a save before wrote it so. From outside is a `SessionEnd` with reason `other` for Claude (its catch-all, which a signal gives; the user quitting gives another) or `exit` for Gemini (which a signal and `/quit` both give, so a Gemini session quit just before the close is resumed; `AgentKind::outside_end_reason`), and an agy terminal seen back at its shell. An end logged earlier, or an agent killed with no hook at all, is what the log says. A server that starts and finds it rebuilds it before it serves (`native/restore.rs`): new ids, every terminal a fresh shell in its directory (in `$HOME` if that is gone). A terminal whose saved session is not over, and whose directory is still there, gets the kind's resume command (`AgentKind::resume_command`: `claude --resume <id>` for Claude, `gemini --resume <id>` for Gemini, whose sessions are kept per directory, and `agy --conversation <id>` for Antigravity; only an id shaped as a UUID, 8-4-4-4-12 hex digits, as each kind's hooks give: a session not over saved with another id gets a plain shell and is counted by kind) typed into its new shell once the shell first writes something (its rc files have run), or after 3 s if it stays silent, so quitting the agent leaves a prompt. Until then the terminal's input is held behind the command (ticket 59, `Input::hold_behind`, set before the server takes connections): keys typed there wait, under the same 64 MiB cap (a refusal's notice once until the program takes its input), and go right after the command, in order (to the agent once it reads its input), so they are neither mixed into it (`eclaude --resume …`) nor lost; the shell's replies to its terminal queries are never held. `PADDOCK_RESUME_WAIT_MS` replaces the 3 s, for tests that keep a shell silent; the server keeps it from its shells. Typing the command before the terminal takes input would put it ahead of the rc files, which may read it. A shell whose startup asks something (an update prompt, a passphrase) before it writes anything else may still take the line. The new server takes that session as seen in the new terminal until its hooks say otherwise, so a restart before the agent reports keeps it. The resumed agent reports under the same session id from its new terminal, in the new server's log, so the dashboard shows it once, as the same session. Any other agent is not restarted. The app starts the server first when the file is there (`Backend::resume`), and shows "restored N spaces" once, with ", resumed M sessions" when it typed any resume command and ", could not resume 1 gemini session" for the sessions it could not, by kind (`Request::TakeRestored`, answered with both counts and the kinds not resumed, `Restored::cannot_resume`, left out when none and read as none from a server that never sends it, so protocol version 2 stays; whether the agent then found its session is not checked). Scrollback (ticket 47, `native/scrollback.rs`): each terminal has a scrollback name (`ScrollbackName`: the server's instance id and its number, `<instance>-<n>`), which `layout.json` keeps with it (`scrollback`, left out when none). A server that ends (SIGTERM, as an upgrade's restart sends, SIGINT or SIGHUP) writes, before the layout, each tab terminal's normal screen with its scrollback, as text with its colours (SGR) and no trailing blank lines, to `scrollback/<name>` (the directory mode 0700; each file its newest 1 MiB from a line's start, written as `layout.json` is: a temp file, mode 0600, synced, renamed). These files, and that last `layout.json`, are written with the state locked, unlike the layout offered while the server runs: the text is read from the emulators under the lock, and the server hangs its shells up under it right after. A server killed outright writes none, so its terminals come back with the scrollback last saved, if any. A restored terminal keeps its name, and its file is fed to its emulator before its shell's first output: only text, tabs, new lines and SGR sequences of it (other CSI and escape sequences and control strings such as OSC, by `ESC` or C1, are dropped whole, other controls dropped, and bytes not UTF-8 replaced, so nothing in it is acted on or answered), under a dim line `--- scrollback saved <local time> ---` from the file's time. The attach replay then carries it to the app, so it scrolls and is searched in copy mode like any scrollback. A name that is not one (`[A-Za-z0-9-]`, at most 32), or a file missing or unreadable, restores that terminal without it, logged; it never stops the restore. Every write of `layout.json` removes the files in `scrollback/` it names no terminal for (a closed split, tab or space, a float, a file half written, and any directory in their place), and a layout of no space removes the directory. An empty file starts clean; one that cannot be read, holds no layout the server can rebuild, or has a space whose shells do not start, is renamed aside (`layout.json.bad-<seconds>`) before anything is written over it, and logged.
  - *Protocol* (`native/protocol.rs`): frames of a big-endian `u32` length, a kind byte, then a JSON `Message` (kind 0), a terminal's output from the server (kind 1: id length, id, bytes), or a part of one input to the server (kind 2: id length, id, how many bytes of the input follow as a big-endian `u64`, bytes), or an upgrade (kind 3, JSON, frozen whatever the version; see *Upgrade*). Both sides first send `Hello { version, pid, instance }` (the server's instance id; 0 from a client, and left out reads as 0, which a client takes from a server as an error, so it never reads a `native-0` log); a side that reads another `protocol::VERSION` stops, and paddock says which version the running server (and its pid) speaks (`OtherVersion`); paddock then asks whether to upgrade it in place to its own binary (`std::env::current_exe`; see *Upgrade*), before taking over the screen, yes the default; on no, or with no terminal on stdin to ask, it stops with the same words. How the upgrade went is told by what runs after it (`Client::upgrade_other`, `Upgraded`): the same server (its pid) answering at this version within 5 s means it is done (also when its `Done` was lost), while another pid means the old one ended and another started since; and paddock opens on it with "paddock server upgraded: programs kept running"; the server still answering at the other version means it did not hand over (`NoHandover`, a refusal, or no answer), so paddock prints why and asks whether to restart it (no the default); no server answering means it failed after the switch and ended, programs and all, so paddock waits for its lock to go, says so, and goes on as after a restart, with "paddock server upgrade failed: its programs ended". To restart, on yes it sends SIGTERM to the process holding the server lock if that is the pid the hello named, waits for the lock, removes a socket left over, and starts a new server, which rebuilds the layout the old one saved as it ended; on no, or with no terminal on stdin to ask, it stops with the same words. Then a client sends `Request`s and reads a `Reply` each: one connection per request, except a border drag's `DragBorder`s, which share one connection the client keeps for drags (a broken one is replaced once, as moving a border to a size twice moves it once); a reply is the answer, or a typed refusal (`Refusal::Ending` while the server ends, so the client starts the next one; else why it failed). A frame from the server is at most 256 MiB, one from a client 16 MiB, read as it comes; a connection closed within a frame is an error. A client that finds no server, or a server version it cannot talk to, says so as different errors: the first is an empty answer to a query, the second is reported (paddock, `paddock worktree` and `paddock debug state` check it first, `Backend::check`); `paddock debug state` answers from the server this way, and only making a space starts one.
  - *Attach and lifetime:* `Request::Attach` makes the connection the attached client of its space (paddock attaches every space, one connection each, as it does tmux's): any other client of that space is let go (its connection closes). Each hears its own space's output and notices, and every one hears `SpacesChanged`, as each space's tmux control client does. One lock guards the whole state, and each terminal's reader thread feeds its emulator and queues the bytes for the attached client under it; the attach resizes the space, then under the same lock queues the reply (structure and sizes) and each terminal's snapshot (`Emulator::snapshot`: scrollback, the saved normal screen and the alternate one, cursor, pen, modes and each screen's kitty flags, plus modifyOtherKeys from `KeyModeScanner` and the scroll region (DECSTBM) and origin mode, which the server reads from the output as alacritty keeps the region private; so a program reattached at the same size, which gets no resize and so does not redraw, scrolls its region on the client as on the server). So the snapshot holds exactly the output before it and the stream continues after it. A writer thread per client sends the queue, so a slow client never holds the lock. A client more than 16 MiB behind for 5 s (or 128 MiB behind at all) has stopped reading, not just paused, and is let go (its connection closed), as is a replaced one, once it has read its last frames or after 1 s. A server that ends on purpose (its last terminal, SIGTERM, `Stop`) sends `Ended` first, as it hangs every shell up, and exits only once every client it is letting go (an ended space's too) has read its last frames or 1 s has passed (a second thread ending it meanwhile, as a float's command ending after its space ended with its last tab, waits for the first); once ending it refuses `Attach`, as it does new spaces and floats. A client whose connection ends without it (let go, or the server failed) gets `Event::Lost`: paddock quits saying so, as its terminals may run on (unless the server said it upgrades, see *Upgrade*). After `Attach` a connection only sends input, `Resize`, `ResizeFloat` and `Detach`: anything else closes it, as a reply would land among the stream's frames. Input and query replies go to a writer thread per terminal, and queuing them never waits: so the connection goes on reading, and a resize or detach behind input to a program that does not read gets through. One input is one batch of keys or one whole paste. paddock sends it as parts of at most 64 KiB (`Frame::Part`, each saying how many bytes of the input follow), so a paste of any size fits the server's frame limit. The server collects an input's parts and queues it only once all have come, all at once; an input whose connection ends before its last part (a takeover, a client let go) is discarded whole, so a program never gets part of one, and is never left in a bracketed paste. The server never drops input it has queued. At most 64 MiB of input waits for one program: an input that would take what waits past that is refused whole, and paddock says "input refused: it would take what waits for vim past 64 MiB", with one line in `server.log`, once per episode (an episode ends when the program has taken all that waited). Replies to a program's queries count against the same 64 MiB: one that would pass it is dropped quietly, and never tells. Each part must say how many bytes still follow so that they add up to what the input's first part said; a part that does not (or one for another terminal mid-input), or a terminal-output frame from a client, is a protocol error that closes the connection. So a server holds at most 64 MiB of queued input and replies per terminal, plus one input being collected per connection (at most 64 MiB: a bigger one is refused without keeping its bytes, and the parts must add up), and 128 MiB of output per client. A writer that fails ends: its error is logged, and nothing more is queued for it. Both kinds of queue are `native::queue::Queue`: unbounded, to a thread of its own, counting the bytes that wait, so whoever queues decides how much is too much. A shell's last output is read before its terminal is forgotten (up to 0.5 s, as a program left in the background can hold the PTY open). A resize answers with a changed structure; a space's last terminal ending sends `Ended`. Closing paddock (`Request::Detach`) leaves the shells running; not carried by the snapshot: charsets, the title and hyperlinks.
  - *Upgrade* (`native/handover.rs`, [ADR 0009](adr/0009-server-hands-terminals-to-a-new-binary.md), ticket 50). `paddock server upgrade [<binary>]` hands the running server's terminals to the binary it is run as (or `<binary>`, made absolute), so programs keep running: `Backend::upgrade(exe)` (`Client::upgrade`), which the version-mismatch prompt calls too (ticket 51, see *Protocol*). It reads the server's hello whatever its version and answers with a frame of kind 3, `Upgrade::Ask { exe }`, which every server since reads in place of a hello, whatever version it speaks (the frame is frozen). The server refuses a relative `exe`, hands over to one binary at a time, and answers `Upgrade::Probed` just before its `exec`, then `Upgrade::Done { pid }` or `Upgrade::Refused(why)`. The client tells apart a connection closed before any answer (a server from before: `NoHandover`, and the command says to start paddock and answer yes to the restart it offers), one closed after `Probed` (the server ended as it took over), a broken frame, and no answer within 60 s. The server first writes the handover record (`handover::FORMAT` 1, apart from the protocol's version) to `handover.tmp` in the state directory, removed once open, with its state locked only to take it: the instance id, the last id given, the current space and the restored count; every space, tab and float with their ids, names, trees, shares, focus, focus order, zoom and the tabs current before; every terminal's id, pid, tty, size, whether it was reaped, its PTY master's descriptor and its snapshot (the attach's), and a resume not typed yet with the input held behind it (see the end of this paragraph); and the descriptors of the lock and the listening socket. It runs `<exe> server --check-handover` on it, for at most 10 s, serving on meanwhile: only exit 0 with `paddock handover ok` is a yes, so a binary of another format, or an older paddock that prints its usage, refuses, and its first line of stderr goes back. Its output is read without waiting and closed with it, so a program it leaves running holds nothing of the server's. Then the server takes its state lock, once every program has taken its queued input (else, after 2 s, "input still waits for vim in %3"), and `layout.json`'s writer's lock, and keeps both: a reader waits for output with `poll` with the lock let go but reads it only holding it, and a waiter sees an exit with `waitid(WNOWAIT)` and reaps and marks the program only holding it, so with it held no output is half taken and no program half reaped. It writes the record again, as it is now, and `layout.json` (whatever the 250 ms gap), sends `Probed`, clears close-on-exec on the record's descriptors, the record's and the asking connection's, and lets the attached clients go (see below), and `exec`s `<exe> server --take-over <record> <connection>`; any error before (or a failed `exec`, which puts close-on-exec back) lets the lock go and leaves the server as it was. The new image keeps the pid (so the lock, its pid, the socket and its backlog, and the programs as its children), the instance id and every id; it rebuilds each space, each terminal with a fresh emulator fed its snapshot (the replies it provokes dropped), starts its reader and waiter (`waitpid` by pid; one reaped before is not waited for), rebuilds its view of the agents' sessions (`Seen`, in `Shared::new`) by reading its hook log, the same instance's, again from its start (not seeded with sessions resumed moments before, which their hooks report soon), answers `Done`, logs "took over as pid N" and serves on, without binding, locking or reading `layout.json`. One that cannot answers `Refused` (saying it has ended) and exits, hanging its programs up; the next start rebuilds `layout.json`, as written at the switch. Before `Probed` the server tells every attached client `Notice::Upgrading` (protocol version 2) and lets it go once it has read that (at most 1 s). paddock (`Event::Upgrading`, `App::upgrading`), once told on any space, takes the end of every space's connection as the upgrade, not a lost server (also one let go before it read the notice): only once every space's connection made before the notice has ended (one made meanwhile is to the new server) does `App::reattach` close the old connections (each numbered, `Event::Backend::connection`, so what a replaced one still reports, up to its end, is left out) and ask until the new image answers (up to 10 s, as the old one takes connections until its `exec` and closes them unanswered), attaches every space again in the same order with the same one current (each space's tab and focus are the server's), and says "paddock server upgraded: programs kept running". After a failed `exec` it attaches to the old server; one it cannot talk to (another protocol version, or failed) makes it quit, saying why, and no server at all (the new image failed and ended) makes it say the new server did not take over (see `server.log`). Keys typed during the switch are lost; a paddock more than 1 s behind on every space misses the notice and quits as on a lost server; a resume command not yet typed (an upgrade within about 3 s of a restore) is handed over with the keys held behind it (`HandedTerminal::hold`: the command, whether the shell has written anything, and how many held bytes follow the snapshots, read as none from a record without it, so `FORMAT` stays 1), and the new image holds them and types the command as the old one would, its 3 s counted again from the switch. A paddock from before reads the held bytes as more than the record holds and refuses the upgrade; with none held it drops the resume, as it always did.
- **One instance at a time.** A second launch offers to take over from the first.
- **State** lives in `~/.local/state/paddock/`: the native server's socket, lock, log, `layout.json` (tabs, splits, sizes and focus; tmux holds them on the legacy backend) and `scrollback/` (each terminal's, saved as the server ends), the sidebar width, dismissed rows, hook events and logs. **Config** lives in `~/.config/paddock/config.toml`: prefix, keys, how long the resize keys repeat, colours, the sidebar width, floats, which notifications to send, where worktrees go, where new tabs start and the External group.
- **Hooks.** The paddock plugin (see Plugin) carries them in `plugins/paddock/hooks/hooks.json`: the events of `hooks::EVENTS`, with the same groups (no matchers) as `paddock hooks install` writes. Every hook calls `paddock hook <event>`, which finds its terminal through `backend::hook_terminal` (on the native backend `$PADDOCK_PANE`, on tmux `$TMUX_PANE`) and appends the event to the state directory, so tasks created while paddock is closed still appear. An event from no terminal of paddock's (neither backend's variables, another server's or another tmux's, no pane) is an external session's: it goes to `events/external.jsonl`, keyed by its session id, without a pane (the record's `pane` is left out, so older logs read as before); one without a session id is dropped. This runs for every agent on the machine, so it stays as cheap as a paddock terminal's: drain stdin, one append, plus the same git read of the branch on the events that may switch it (Claude: `SessionStart`, `UserPromptSubmit`, `SubagentStart`/`Stop`, a Bash `PostToolUse`; Gemini: `SessionStart`, `BeforeAgent`, a `run_shell_command` `AfterTool`; Antigravity: `SessionStart`, `PreInvocation`); no tmux call. Once that file passes 4 MiB, paddock compacts it, when it opens and (checked with a `stat` every few seconds) while it runs: it keeps the last day's records, and of those at most the newest 2 MiB, so the next trim is 2 MiB of hooks away however busy the day was (a hook appending meanwhile may lose its line; the next hook or `claude agents --json` makes up for it). `claude agents --json` is used to discover sessions and reconcile state.
  - *Plugin hooks* find `paddock` on `PATH` (Homebrew and `cargo install` put it there), as `command -v paddock >/dev/null 2>&1 || { cat >/dev/null; exit 0; }; export PADDOCK_HOOK_SOURCE=plugin; paddock hook <event> >/dev/null 2>&1 || true`. The hook always exits 0 and prints nothing, whatever `paddock` is on `PATH`. Without one, it drains stdin and exits 0: a missing command would exit 127, which Claude shows as a hook error. Some other `paddock` exiting 2 would block `Stop`, hence `|| true`. Its output goes to `/dev/null`, since Claude adds the stdout of `SessionStart` and `UserPromptSubmit` hooks to its context. paddock's own `paddock hook` never prints and always exits 0 anyway; its errors go to `hook-errors.log`. Each hook has `"timeout": 10` (seconds; Claude's default is 600), so a `paddock` that hangs stalls Claude 10 s at most; `SessionEnd` has none, keeping Claude's 1.5 s budget for those hooks, which a longer timeout would raise.
  - *Fallback:* `paddock hooks install` and `paddock hooks uninstall` edit `~/.claude/settings.json` (`$CLAUDE_CONFIG_DIR/settings.json` if set), for users without the plugin. Both take `--agent <kind>`, repeatable, to act only on those agents (see Agent kinds); without it they act on Claude, as they did before agent kinds existed. Supacode's hooks stay; the old tmux-claude-session-manager hooks are removed. These hooks call paddock by its full path. `install` notes when that file enables the plugin (`enabledPlugins` has `paddock@paddock: true`, as `claude plugin install` writes it at user scope; other scopes are not checked). `uninstall` is the way to move to the plugin, after the plugin with hooks is installed and sessions restarted, so no event is lost in between. Both commands say to restart running Claude sessions: the plugin's hooks read `settings.json` at once, but a running session may still run the settings hooks it loaded before.
  - *Gemini CLI*'s hooks are not in its extension (see Plugin): `paddock hooks install --agent gemini` (and a plain `paddock hooks install` when `gemini` is on `PATH`) writes `hooks::GEMINI_EVENTS` (`SessionStart`, `BeforeAgent`, `AfterTool`, `Notification`, `AfterAgent`, `SessionEnd`) to `~/.gemini/settings.json` (`$GEMINI_CLI_HOME/.gemini/settings.json` if set), in Claude's shape: each group one command hook, `paddock hook --agent gemini <event>` by paddock's full path, with `"timeout": 10000` (milliseconds; Gemini's default is 60000) and no matcher. Same atomic write and same own-entry detection (`is_ours`) as Claude's; the user's other hooks, `hooks.disabled` and every other setting stay, and `uninstall` drops only a list it emptied itself, for Claude's settings too (before, it also dropped empty lists the user had). Gemini parses a hook's stdout as JSON, so paddock printing nothing matters here too. Not `BeforeTool`: it runs before the permission prompt, so it adds nothing `AfterTool` does not and delays every tool; not `BeforeModel`/`AfterModel` (every streamed chunk), `BeforeToolSelection` or `PreCompress` (fired asynchronously, also for a manual `/compress` while idle). Gemini's settings may hold comments; paddock's JSON parser refuses them and leaves the file untouched.
  - *Antigravity CLI*'s are not in its plugin either: `paddock hooks install --agent agy` (and a plain `paddock hooks install` when `agy` is on `PATH`) writes paddock's entry in `~/.gemini/config/hooks.json`, a file keyed by hook name, not by event: `{"paddock": {"<event>": [{"type": "command", "command": "<paddock> hook --agent agy <event>", "timeout": 10}]}}` for `hooks::AGY_EVENTS` (`SessionStart`, `PreInvocation`, `Stop`, which take their handlers directly, without a matcher group), `timeout` in seconds (agy's default is 30). `install` replaces that entry whole, so it is idempotent; `uninstall` removes only that key, whatever else calls paddock; the user's other named hooks stay. Same plan-then-apply, atomic write and never creating a file on `uninstall`. agy reads a hook's stdout as JSON, and `PreToolUse` needs a `decision` in it, so `paddock hook --agent agy` prints `{}` (a no-op for every event) and paddock does not hook `PreToolUse`; `PostToolUse` and `PostInvocation` change no state. `~/.gemini/antigravity-cli/settings.json` and workspace `.agents/hooks.json` are not touched.
  - *One record per event.* Claude runs both copies when both are installed: it merges identical handlers across settings files, but a plugin's copy stays separate. The rule: a plugin hook (`PADDOCK_HOOK_SOURCE=plugin`) records nothing when the user settings hold paddock's own hook (any command that runs `paddock hook`) for that event; the settings hook records it. The plugin defers rather than the settings hook, because the settings hooks are what the user set up by hand, and because a plugin without hooks (0.0.3) may be enabled: deferring to "the plugin is enabled" would drop every event there. The check runs after stdin is drained and before the terminal is looked up, so external sessions' events are recorded once too; only the plugin's hook reads the settings; settings that cannot be read count as no hooks, so the plugin's hook records. The marker is an environment variable, not an argument, so an older `paddock` given the plugin's command still records instead of failing on usage. Known gaps:
    - Settings hooks pointing at a binary that is gone record nothing, and the plugin's defer to them. Re-run `paddock hooks install`, or `uninstall` to rely on the plugin.
    - An older `paddock` first on `PATH` ignores the marker, so with both installed it records each event twice.
    - Only paddock's own hook in settings counts (`is_ours`: the command's program is `paddock`, followed by `hook`). A hook written by hand that wraps the call (`sh -c 'paddock hook Stop'`, or the plugin's command copied in) does not, so with the plugin each event is recorded twice. Matching any command that contains `paddock hook <event>` was rejected: a false match makes the plugin skip an event the hand-written hook may not record, and losing events is worse than doubling them; `is_ours` also decides what `uninstall` removes. Use `paddock hooks install`, or the plugin alone.
    - Project and local settings are not read.
- **Commands.** `paddock`, `paddock keys` (prints the default keys as TOML), `paddock hooks install|uninstall [--agent <kind>]...`, `paddock worktree new|open|list|rm` (see Worktree command), `paddock help` (also `-h`, `--help`), `paddock version` (also `-V`, `--version`), and the internal `paddock hook [--agent <kind>] <event>`. Like hooks, `paddock worktree` runs and exits; it is not a daemon (ADR 0003).
- **Any terminal app.** Only standard VT features; truecolor with a 256-colour fallback; the UI uses the terminal's 16 ANSI colours so it follows the user's theme; copying goes through `pbcopy` and notifications through `osascript` on macOS, `wl-copy` (Wayland, when `WAYLAND_DISPLAY` is set, then `xclip` when `wl-copy` cannot be run or fails: XWayland; if both fail, `wl-copy`'s error is shown) or `xclip -selection clipboard` and `notify-send` on Linux (its message with `&`, `<` and `>` escaped, as servers read it as Pango markup), chosen in one place (`src/desktop.rs`, the desktop's platform seam, as `src/backend/native/proc.rs` is the server's); `PADDOCK_COPY_COMMAND` names another copy program and `PADDOCK_NOTIFY_COMMAND` another notifier (given the platform's arguments). A failure to notify is said once in the tab bar; a copy tool that cannot be run (missing, most likely) is said once too (`SayOnce`, `src/app/desktop.rs`), while one that runs and fails is said on each copy, with the first line of its stderr (at most 4 KiB read, kept in an unlinked temporary file, not a pipe: `xclip` and `wl-copy` leave a child serving the clipboard that would hold a pipe open). Opening a PR needs no opener of paddock's: `gh pr view --web` picks the browser (`open` on macOS, `xdg-open` or `$BROWSER` on Linux); no key depends on Option/Alt. paddock makes no network calls itself; PR status asks the GitHub CLI (`gh`), which does (see Pull requests).
- **Agent kinds.** Each session belongs to an agent kind (`sessions::AgentKind`): `claude` (Claude Code), `gemini` (Gemini CLI, tested with 0.64) or `agy` (Antigravity CLI, tested with 1.4.3). The kind travels with each hook record (`kind`, left out of the log for Claude, so logs written before kinds replay as Claude's and Claude's lines are written as before), then with its session (the kind of its latest event) and its row. What differs between agents matches on the kind where it is used, so a new agent is one more arm in each, not a rewrite: how a payload becomes a record (`log::record`), the state an event leads to (`state_after`), whether it starts a conversation, finishes a turn or ends one, whether the branch is read after it (`needs_branch`), which settings file `paddock hooks` edits and which events it writes (`hooks::settings_path`, `events`). Claude's hooks call `paddock hook <event>`, as they always did, so hooks installed before kinds, by users and by the plugin, keep working; `paddock hook --agent <kind> <event>` names the kind. A `paddock hook` with arguments it does not understand (an unknown kind) still drains stdin, records nothing, writes the error to `hook-errors.log` and exits 0. `paddock hooks install|uninstall` without `--agent` acts on Claude, as before (the `claude` CLI need not be on `PATH`), on Gemini when an executable `gemini` is on `PATH`, and on Antigravity when `agy` is. Either reads and edits every settings file it acts on before writing any, so a file it cannot read or parse (invalid JSON, such as Gemini's with comments) makes it exit 1 naming that file, with no file changed; each file is written atomically, but a write failing partway (a full disk, say) leaves the files written before it; `uninstall` leaves a missing file missing; with `--agent`, only on those named, and an unknown kind changes nothing and exits 1. Claude only: fork (`claude --resume --fork-session`; another kind's session says `fork needs a Claude session`), subagent rows (only Claude's payloads carry `agent_id`; Gemini's and Antigravity's subagents are not shown), and the `claude agents --json` snapshot (sessions it finds are Claude's; a live Gemini or Antigravity session is left to its hooks). Gemini's events: `SessionStart` (any source: startup, resume, `/clear`) starts a conversation, idle; `BeforeAgent` (a prompt) is running; `Notification` with `notification_type` `ToolPermission` is waiting; `AfterTool` is running again (after a granted permission nothing else fires until the tool is done, so the row stays waiting while the tool runs); `AfterAgent` finishes a turn, done until seen, like Claude's `Stop`; `SessionEnd` ends the conversation: with reason `clear` the terminal's session goes on (Gemini 0.64's `/clear` sends `SessionEnd` `clear` with the old id, then `SessionStart` `clear` with a new one, as Claude does), otherwise it is stopped; an external session ends on any `SessionEnd`. Antigravity's events (camelCase payloads with no `cwd` and no event name, which goes on paddock's command line): the record's session id is `conversationId`, its directory the first of `workspacePaths` (a `file://` URI read as a path); `SessionStart` starts a conversation, idle; `PreInvocation` is running; `Stop` with `fullyIdle: true` finishes a turn, done until seen (with background work left it changes nothing). agy has no end event, no prompt event and no wait hook; waiting comes from its status reports (see Program status). Its session ends when its terminal closes, or when the terminal's foreground command (`Backend::terminal_commands`) is a shell (`sh`, `bash`, `zsh`, `fish`, `nu`, `xonsh`, `elvish`, `pwsh` and the like, a login shell's leading `-` ignored), read every 3 s next to the snapshot, only while a live Antigravity session runs in a terminal; a list read before the session's last event is ignored (it may predate agy). Not "any command but `agy`": agy may hand the terminal to another program for a while. An external Antigravity session has neither: it ends only by `external_timeout`, and is never waiting. Rows show their kind as a tag: the dashboard's AGENT column (last, and the first to drop), the end of the sidebar agent's second line when it fits there; a tab named after its session takes the kind's tag (`claude`, `gemini`, `agy`).
- **Program status (OSC 7501).** A program may write `ESC ] 7501 ; state=<state>:app=<app>:kind=<kind>:msg=<base64>... ST` (ST is `ESC \` or BEL) to say whether it is `idle`, `working`, `done`, `blocked` (on a `permission`, `question` or `auth`) or `error`, or `clear` its reports; it asks first with `ESC ] 7501 ; ? ST` followed by `CSI c`, and takes `CSI c`'s answer arriving first as no support. The spec is Rex's "program status" page (superlogical.com), after Mitchell Hashimoto's proposal. agy 1.4.x reports with `app=antigravity` when the terminal answers, or when `AGY_CLI_OSC7501=on`. tmux answers `CSI c` itself and drops the OSC, so paddock could never answer in time: its tmux config sets `AGY_CLI_OSC7501 on` in the server's global environment, so every new terminal has it. Each terminal's raw output passes a scanner (`terminal::program_status`) before copy mode can hold it back; it only reads, and the emulator draws nothing for the OSC. Reports with `app=antigravity` become records (event `OSC7501`, the state in their own `status` field, `sessions::ProgramState`, no session id; only agy's records have it, so Claude's and Gemini's lines are written as before) appended to the server's hook log, but only while a live Antigravity session runs in that terminal and when the state differs from the last report recorded for it since a hook last changed its state (a new conversation starts over too); a report counts as recorded only once its line is written. A hook reaches the app up to a log poll (200 ms) after it ran, so agy's first report can come before its `SessionStart` is folded: the latest report of a terminal with no agy session waits, in memory only, and after each batch of hooks it is, in this order: if a live agy session there started at most 1 s after the report came, dropped when a hook other than that start has since set the session's state after the report came (the report is older news: a pre-start `idle` before a `PreInvocation` in the same batch), else recorded (written with the session's latest record's time if that is later, so a replay folds it where it was folded live); dropped, if the live agy session there started more than 1 s after it (it was about an earlier one); otherwise kept waiting, and dropped by the first batch after it is 1 s old (until then nothing is written). The 1 s slack can admit a report made up to 1 s before a resume of the same conversation, as about the resumed session, so they fold in the order they happened with the hooks (a hook's line is there first when it ran first) and replay on reopen. A report folds only into a live Antigravity session in its terminal: it never makes a row, and other programs' reports are ignored. `working` is running, `blocked` waiting, `done` and `error` finish a turn, `idle` is idle (keeping done), `clear` changes nothing. agy reports a turn's end twice (`done`, then its `Stop`), so for agy a finished turn alerts once until the next running event, not on each; for that, an agy report naming no conversation matches the pane's last alert, a rule that applies to agy's events only. An `idle` report never alerts: only a finished turn does (agy reports idle when it starts and as it quits). Any program in an agy session's terminal can write such a report and set the session's state. Reports written while paddock was closed are not seen. Text about any session says agent (`no agent sessions yet`, `an agent is running: close? y/n`); text about a Claude-only feature says Claude.
- **Refresh.** Git info refreshes on hook events and every few seconds for the dashboard's rows while it is open. Pull requests refresh on a thread of their own, when the dashboard opens and every `[github] refresh_secs` while it is open or the sidebar shows (see Pull requests).

## Interface

### Layout

- Left: the closable, resizable **sidebar** (32 columns, or `[sidebar] width`; `C-a {` / `C-a }` or dragging its border change it by 2 columns between 16 and half the screen, and the last width is kept in the state directory), in two sections (after herdr):

  ```text
   SPACES
   ● api-server
     ~/project/api  main
     paddock
     ~/project/paddock  feat/x

   AGENTS
   ● api-server  waiting
     api-server · claude
  ```

  SPACES has two lines per space: a dot in the most urgent state of its agents (none without agents), its name (the tmux session name) and, at the end of that line, the git status of the branch checked out in it, as the dashboard writes it (`ui::StatusText`, shared): uncommitted lines `+200` (green) `−10` (red), both unless both are zero, untracked files counting as added, then commits ahead of and behind upstream `↑2↓1` (dim, each left out at zero); nothing on a detached HEAD (gated on `git branch --show-current`, not the short commit shown) or outside a repository; on the selected (reversed) line the line changes take no colour, which would turn into a background. The status keeps two cells or more from the name: short of room, the name is cut with `…` down to its first 8 cells, and past that the status is left out whole, never cut (the name then shows as it would without one). Then, dim, its directory (that of its first tab's first pane, home as `~`) and the branch (the short commit if detached, nothing outside a repository), and at the end of that line, two cells or more after them, the branch's pull request: `#123` in its state's colour (as on the dashboard) and its checks mark (`✓`, `✗`, `•`, dim; none without checks), no review; nothing without a PR (see Pull requests). Short of room, the path loses its start (`…`) first, down to `…` alone, then the PR mark is dropped, then the branch loses its end. A worktree space's lines start a cell further in and end at the same edge. Directories, branches and the branches' status are read on the git thread, at start, on hook events and every few seconds, never per frame, each directory and branch once per poll however many spaces and tasks share it (`watch::read_watched`); `C-a r` rereads the place at once and keeps the last status only if the directory and branch are the same, until the thread's next read; the second line stays empty until the first read. The current space (the one whose tabs are shown) has its own background over both lines (`[colors] current_space`, a 256-colour index or `#rrggbb`, default 236). AGENTS lists every main agent session that has not ended (see Task tree) in an open pane, in any space, in space, tab and split order (never by state, so a state change does not move an agent and the list never jumps while you read it): a dot, its label and state, then, dimmed, its space and tab and, at the end of that line under the state, its agent kind's tag (`claude`), only when it fits after the whole place, which is never cut for it, with a blank line between agents. The current agent (the one in the focused terminal of the page shown) has the current space's background over both its lines. Subagents and task rows stay in the dashboard. While the sidebar has the keyboard, the selected space or agent is reversed. `C-a s` gives it the keyboard on the current agent if the focused terminal holds one, else on the current space; `C-a w` always on the current space; either shows a hidden sidebar.
- Right: the **session view**, the current item's tab bar and the current tab's terminals (splits).
- The tab bar follows herdr's look: a darker row (`[colors] tab_bar`, default 235) with each tab a filled block, its name centred, at least 8 cells wide, one blank column apart; the current tab has the accent colour (`tab_current`, default the terminal's blue) with dark text, the others a dark grey (`tab`, default 237) with dim text, and a name the user gave is bold. A `+` after the last tab opens a new one. When the tabs do not fit, `<` and `>` scroll by one and `…` marks hidden tabs; switching tabs scrolls the current one into sight, about in the middle. The wheel over the bar switches tabs; `C-a <` and `C-a >` move the current tab (no wrap). A tab is named after what runs in its focused pane (`claude` while Claude runs there, else the command, or the directory for a shell) until the user renames it. A tab holding a waiting, done or idle agent gets a `●` in that state's colour before its name.
- The **dashboard** opens as an overlay (`C-a o`) and holds the task tree: the list on top (as tall as its rows, at most about 40% of the height, with a blank line under its column header and another under its rows), the live preview below it in a rounded border with its title in the top border, and the keys on its last line, under that border. On a short screen the preview goes first.
- A new space (`C-a C`) and a new tab (`C-a c`) start a blank shell in the focused terminal's directory; paddock notices when Claude starts in it. A new space first asks for its name, prefilled with `space-N` (`Enter` keeps it); a new tab does not ask.
- **Splits** are a tab's panes, laid out by tmux (ADR 0006): `C-a |` and `C-a -` split (the new pane takes the focus), `C-a h/j/k/l` move the focus (`select-pane -L/-D/-U/-R`), `C-a =` evens out the focused split (`select-layout -E`), `C-a x` closes one. **Resizing** stays in tmux too, so sizes survive detaching: `C-a H/J/K/L` (`resize_left/down/up/right`, no direct chord by default) are `resize-pane -L/-D/-U/-R 2` on the focused pane, which moves the border after it (before it for the last pane of a row or column), stops at 1 cell without an error, and unzooms first. After the prefix, a resize key opens a repeat window (`[keys] repeat_ms`, 500 by default, like tmux's `repeat-time`; `0` never opens one) in which the resize keys run again without the prefix, each restarting the window (`PrefixKeys`); any other key closes it and is read as usual, and a direct chord opens none. Dragging the border between two splits (`Press::Split`) moves it live: on press paddock reads `#{window_layout}` (tmux 3.8's JSON tree; another format means no drag) and picks the pane whose `resize-pane` moves that border, as the pane beside it may not (one last in its own row moves the border before it) (`backend::tmux::layout`); the drag sends absolute sizes (`resize-pane -x/-y`) at most every 40 ms, the last on release, and `%layout-change` redraws. A press on a border never starts a selection nor reaches a program, and a zoomed tab has no borders. paddock draws each pane where `list-panes` places it, with a line in the cell tmux leaves between two panes. **Zoom** (`C-a z`, `zoom`, no direct chord by default) is tmux's `resize-pane -Z` on the focused pane: it fills the window and the others are hidden, still running; the same key unzooms, giving every pane its place back and keeping the focus. The zoom is read from tmux (`#{window_zoomed_flag}` in `backend::tmux::structure::FORMAT`, `Tab::zoomed`), so it survives detaching and a zoom made from `tmux -L paddock attach` shows; the `%layout-change` tmux sends on zoom and unzoom refreshes the structure. While zoomed, `list-panes` still gives the hidden panes their old places, so paddock draws, clicks and borders only the focused pane (`Tab::shows`), a hidden pane does not count as on screen (copy mode in it ends; a turn finished in it stays `done`), and the tab bar puts a `Z` after the tab's name. Moving the focus, splitting, evening out and closing a pane unzoom in tmux itself (`select-pane` without `-Z`, `split-window`, `select-layout -E`, `kill-pane`), so paddock adds nothing for them; a jump to a hidden pane (`C-a a`, the finder) also clears the zoom in paddock's copy of the structure at once (`Tab::focus`), so no frame draws the pane at its hidden place before tmux reports. `zoom` is not among the commands that keep a float shown: with a float up, `C-a z` hides it, then zooms.
- **Space root:** each space has a root directory, stored in tmux as the session option `@paddock-root` (`backend::tmux::server::ROOT_OPTION`), so it lives with the space (ADR 0006). `Backend::new_space` (tmux: `Server::new_session`) sets it to the directory the space is made in, so every way of making a space sets it: `C-a C` (the focused terminal's directory), the first space at start (paddock's start directory), `C-a W` and `C-a O` (the worktree), and `paddock worktree new|open`. It is set in the same tmux run as `new-session` (a command after it in one run targets the new session), so nothing sees the space without it. The value goes through the final-`;` escape only: `set-option` does not format-expand a value without `-F`, so a `#` is stored as is. `C-a R` (`set_root`) sets it to the focused terminal's directory, with a notice (`space-1's root: ~/b`); if that directory is unknown, the root stays and a notice says so. `[spaces] new_tab_dir` picks where new tabs (`C-a c`, the tab bar's `+`) and splits start: `"current"` (default), the focused terminal's directory as before; `"root"`, the root, read from tmux at each new tab or split, so `C-a R` applies at once. A space made before roots has no option, and its first tab's directory (`worktree::space_dir`) serves as its root (`worktree::space_root`); a root that no longer exists falls back to the focused terminal's directory. New spaces, floats and forks are not affected by the setting. The sidebar keeps showing the first tab's directory; the finder's space row shows the root as stored (links kept), with what is checked out at the root itself (`git::head` on the root, read with the space's place in the background and again at `C-a R`), so the branch always belongs to the directory beside it; none outside a git checkout.
- **Floats** (`[floats]`, like tmux's `display-popup` but persistent): the prefix and a float's key (default `G`, running `lazygit`) show a program in a box centred over the whole screen, sidebar included, `width`% by `height`% of it (default 80 by 80, at least one cell inside and at most the screen), framed like the prompt popup: rounded, in the accent colour (`[colors] tab_current`), the command as its title in the top border. The same keys hide it and the program keeps running; showing it again brings back the same program and state. When the program exits the float closes, and the next toggle starts it again. Each space has its own float per key, started in the focused terminal's directory: a tmux window of the space's session, created in the background (never the session's current window) and marked with the window option `@paddock-float` (the key). `list-panes -s` reads the option, and marked windows are kept apart from the tabs, so they never show in the tab bar, its counts, `C-a Tab`'s history, cycling or the sidebar, and hooks and `claude agents` from their panes are ignored (paddock does not follow an agent in a float). The float's window gets its own size on the space's control client (`refresh-client -C @window:WxH`, which later client resizes leave alone; ADR 0006), the inside of the box, sent when it shows and on every relayout. If tmux makes a float current (the current tab closed), paddock selects a tab again; when the last tab closes, the space closes with its floats. One float shows at a time; showing another hides the first. While one shows, every key goes to it except the prefix: `C-a` commands work, and one that changes the page or gives the sidebar or dashboard the keyboard hides the float first (help, showing, hiding or resizing the sidebar, and detaching keep it). Paste goes to it, the mouse inside it goes to its pane, and a click outside does nothing. A float whose key was removed from the config is closed, with its program, the next time paddock opens (at attach, not on later structure reads). The float is made and marked in one tmux run, so it never shows as a tab; if marking fails, the new window is killed by its unique name, so it never stays as a tab. A program that exits within two seconds of starting, before any input (keys, paste or mouse) reaches it, gives a notice (`lazygit exited at once`). Hooks from a float's pane are ignored even after the float closed (paddock remembers the panes of floats it has seen). While a float shows, the tab under it does not count as looked at: an agent there that finishes or waits still notifies. A space's directory (its sidebar row) is its first tab's, never a float's.
- **Prompts** (after LazyVim's input): renaming a tab (`C-a ,`) or space (`C-a $`), naming a new space or a new worktree's branch, the list of worktrees to open, and the questions before a busy close or a worktree delete open a popup centred on the whole screen, over the sidebar, with nothing dimmed behind it: a rounded box in the accent colour (`[colors] tab_current`, the current tab's), its title in the top border (` Rename tab `, ` Rename space `, ` New space `, ` Close tab `, ` Close pane `, ` Close space `, ` New worktree `, ` Open worktree `, ` Delete worktree `; closing a pane alone in its space's only tab says ` Close space `), one line inside. A name starts as the current one (or the default) with the cursor at its end; the box is 40 columns wide, narrower on small screens, and long text scrolls inside it to keep the cursor in sight (by character, wide characters by their width). A question reads `an agent is <state>: close? y/n`. While the popup is open every key goes to it; a click outside cancels it, a click inside does nothing. Asked from the sidebar or the dashboard, it gives the keyboard back to that panel when it closes. A tmux error (e.g. a taken name) shows as a notice in the tab bar once it closes, tmux's reason first (`duplicate session: space-1 (tmux …)`) so it shows even when the notice is cut to the bar's width.
- **Finder** (`C-a g`, `[keys.commands] finder`): a box framed like the prompts and floats, centred over the whole screen, 64 columns by 15 rows or as much of the screen as there is: a text field on its first line and the matching rows under it, best first, the selected one reversed. The rows, each with its kind as a marker: every space (name; its root and the branch checked out there, dim after it), every tab (`space › tab`; its directory and branch: its agent's, else its space's), and every agent (its label; its state and `space › tab`). The dashboard's session rows are the sidebar's agents, so no further session rows are needed; a row is never listed twice for one pane. Matching is fuzzy (`src/fuzzy.rs`, a subsequence scorer: a point per character, more for one right after the last and for one at the start of the text or a word; the best field counts) against the name, the kind, the directory and the branch, case-insensitive unless the query has an uppercase letter; rows with equal scores keep their order. On an empty query `b`, `w`, `i` and `d` show only agents that are waiting (blocked), running (working), idle or done, `a` everything again, and the title reads ` Finder · waiting `; with text in the field these are ordinary characters. Keys are fixed: `Up`/`Down` and `C-p`/`C-n` move, `Enter` shows the selected row (a space: its tabs; a tab: it; an agent: its pane focused) with the keyboard back in the terminal, `Esc` closes, and the text is edited as in the prompts; paste types into the field. A click on a row opens it, the wheel moves the selection, a click outside closes it as `Esc` would. The finder is a mode of the app, like naming, not a float: it takes the whole keyboard (the prefix included), it draws over a float shown, which hides only when a row is picked (`Esc` or a click outside leaves it shown), and opened from the sidebar or the dashboard it gives the keyboard back to that panel on `Esc`. The rows are read from the app's state on every key and draw, never from tmux.
- **Dashboard filter** (`/`, `[keys.dashboard] filter`): a one-line filter under the dashboard's title (` / ` then the text, with the cursor while typing it): the list keeps only the blocks whose session name, state or any task branch fuzzy-match it, the selection stays on a listed line, and the key line reads `Enter keep  Esc clear`. `Enter` keeps the filter and returns the keys to the list, `Esc` clears it and leaves the filter line; the line shows while typing or while it holds text. Paste types into it. The filter is part of the open dashboard, so it goes when the dashboard closes.

### Task tree

- Shown in the dashboard. Levels: session → task.
- A session row is a terminal where an agent runs. Its label is the session name if set, else the tab name if the user gave one, else the directory name, else the agent kind's tag.
- Task rows are the main agent's branch plus each subagent's branch, labelled with the subagent's task description.
- Plain shells and the default branch get no row.
- Everything under a session belongs to it: a session and its task rows form a block, with a blank line between two blocks. Only sessions are selected: moving skips task rows, the whole selected block gets the current space's background (`[colors] current_space`, as in the sidebar; each line keeps its own colours as text), scrolling keeps the whole block in sight where it fits, and every key acts on the session; dismissing it dismisses its task rows with it.
- Rows stay until dismissed (`D`) or until their session ends: its terminal (pane, tab or space) is closed, or its agent quits in it (`SessionEnd`: the session is stopped). A session that ended leaves at once with its task rows, everywhere rows are used (the dashboard, the sidebar's AGENTS, the dots and tab markers, `C-a a`), and replaying the event log on reopen does not bring it back. If it was selected, the session that took its place is selected, and interactive preview ends. A new agent in the same terminal is a new session and gets a row, without the ended session's task rows. `/clear` (`SessionEnd` with reason `clear`) only starts a new conversation in the same agent (Claude or Gemini), so its row stays; subagents still at work belong to the conversation that ended, so their tasks stop all the same. A hook that lands after `SessionEnd` (a subagent's, or a tool's racing it) does not bring an ended session back, nor does a late `SessionStart` from a compaction (`source: compact`); only the agent starting that conversation again (a resume) does. There is no setting to keep ended sessions.
- External sessions (agents outside paddock's terminals) appear dimmed in a group at the bottom, under an `external` line, and close the sidebar's AGENTS under an `EXTERNAL` header, their second line naming their branch (else their directory). They come from hooks (see Hooks) and from `claude agents --json` entries with no paddock pane, keyed by session id (`ext:<id>`); a session later seen in a paddock terminal (resumed there) stops being external. A row's label is the session's name, else its directory's; its state, task rows and git fields follow the same rules as any session's. It leaves on any `SessionEnd`, `/clear` included (the new conversation is another session id), or after `[dashboard] external_timeout` minutes (default 10) with no hook event and absent from `claude agents --json`, since its agent may have been killed without a `SessionEnd` (a kind without a snapshot, Gemini, is kept alive by its hooks alone: waiting, it outlasts that timeout, since a wait sends no hooks and nothing else could say it still runs, and leaves on `SessionEnd`, when dismissed, or once nothing has been heard of it for 24 hours (`WAITING_KEEP_MS`, the external log's retention), so one killed while waiting does not stay forever; in any other state a quiet one leaves until its next hook); old ones in the replayed log stay gone for the same reasons, the same timeouts measured from their last record. `[dashboard] external = false` hides the group and its notifications. The finder leaves external sessions out.

### Fields

| Where | Fields |
|---|---|
| Sidebar space | name, dot in the most urgent state of its agents and, at the end of that line, the branch's status (`+a −r ↑n↓n`) where it fits whole (the name cut down to 8 cells first); then directory, branch and pull request (number and checks), the path cut first, then the mark dropped |
| Sidebar agent | label, state and highlight, space and tab (an external session: its branch, else its directory) |
| Dashboard | state and highlight, branch, ahead/behind upstream, line changes (`+30 −144`, uncommitted), base diff, number of changed files, last commit age, the branch's pull request (number, state, checks, review), else a merged badge |

The dashboard list is a table under a dim header: NAME (the session's label, its task rows indented under it), STATE, ↑↓, CHANGES, BASE, FILES, AGE, PR (the branch's pull request, `#123 open ✓ approved`, else `merged` once git finds the branch in its base; see Pull requests), AGENT (the session's agent kind, `claude`; empty on task rows). Every line puts each value in its column, empty when zero or unknown, so values line up; a column is as wide as its widest value in sight (capped at 12 cells, PR at 34), numbers to the right. When the list is narrow, the name keeps room: AGENT goes first, then the PR column shortens to its number and checks (`#123 ✓`), then it goes, then FILES, BASE, ↑↓, AGE and CHANGES; NAME and STATE always stay, and a name too long is cut with `…`.

### Pull requests

A task row's branch with a GitHub pull request shows it in the PR column, and a space's branch marks it in the sidebar (see Sidebar; `paddock worktree list` gives it too, see Worktree command; `src/github.rs` reads it, `src/app/prs.rs` keeps it fresh):

- **Source:** `gh pr list --state all --limit 20 --json number,state,isDraft,headRefName,statusCheckRollup,reviewDecision,url`, one call per repository (keyed by its main checkout, so its worktrees share it), run in that checkout with `GH_PROMPT_DISABLED=1`, `GH_REPO` removed (set, gh would ask that one repository whatever the directory; `GH_HOST` stays), no stdin, and git's 5 s limit (`git::wait`). PRs match branches by `headRefName`; the highest number wins when a branch has several. `PADDOCK_GH` overrides the `gh` run (the tests' stub). 20, as rolling up checks is slow: on a busy repository 20 took about 3.5 s, 30 close to 5 s, 50 and more timed out. A branch whose PR is older than the repository's newest 20 shows git's `merged` only.
- **Refresh:** a thread of its own, so `gh` never holds up the screen or git's reads. The event loop feeds it what shows PRs (`prs::Wanted`): the open dashboard's tasks, and, while the sidebar shows, each space's directory and the branch checked out there (the pair its line draws; sent again when the git thread reads new places). It asks only while that is not empty, so never while the sidebar is hidden and the dashboard closed: when the dashboard opens, for each repository read 10 s ago or more (`REOPEN_FLOOR`, so toggling the dashboard does not run gh each time), and for each repository every `[github] refresh_secs` seconds (default 60). Repositories are asked one after another, each up to 5 s, so with several slow ones a pass takes a while; it stops before the next repository once the dashboard closes or nothing shows PRs any more (the next pass reads what still shows). `refresh_secs = 0` starts no thread: no `gh` ever runs. Results come to the event loop as `Event::Prs`, by `(directory, branch)` like git's details; the last ones stay shown while new ones are read.
- **Failure:** without `gh`, logged out, with no GitHub remote, or when `gh` fails, prints what is not its JSON, or misses its deadline, that repository has no PR status (the column shows what git knows) until a later call answers. No notice; one line in `gh.log` in the state directory per repository, not again until it has answered.
- **Values:** state open, draft (`isDraft`), merged, closed. Checks, from `statusCheckRollup`: each check counted once, by its latest run (a check run by its workflow and name, a commit status by its context; the latest `startedAt` wins, so a re-run replaces a stale failure); a check run not `COMPLETED` is pending, else its `conclusion`; a commit status by its `state`. `SUCCESS`, `NEUTRAL` and `SKIPPED` pass; `FAILURE`, `ERROR`, `CANCELLED`, `TIMED_OUT`, `ACTION_REQUIRED` and `STARTUP_FAILURE` fail; anything else (`PENDING`, `EXPECTED`, `STALE`, a queued run) is pending. Any failing: `✗`; else any pending: `•`; else `✓`; no checks: nothing. Review, from `reviewDecision`: approved, changes requested, review required; `""` or null: nothing.
- **Cell:** `#123 open ✓ approved` (missing parts left out), its number coloured by state: open green, draft dim, merged magenta (the terminal's purple), closed red; only the number's colour changes, so the line's highlight and background stay. Narrow: `#123 ✓`.
- **`p`** (`[keys.dashboard] pr`): runs `gh pr view --web <number>` in the task's directory, on a thread (30 s at most), for the selected session's main agent's branch's PR, else the first subagent branch's with one. No PR (or PR status off): the notice `no pull request for <branch>`. `gh` failing comes back as a notice `cannot open PR #<n>: <reason>`. While one open runs, `p` does nothing, so presses never stack. An external session's PR opens too: it touches no pane.
- No notifications for PR or CI changes, and nothing is written to GitHub.

### States

- Session: running, waiting, done, idle, or unknown. A session that ended (its agent quit) has no row. A main agent that finishes a turn (Claude's `Stop`, Gemini's `AfterAgent`, Antigravity's fully idle `Stop` or its `done` report) is done while you are not looking at its tab (the current space's current tab, outer window focused), and turns idle once you do. An external session has no tab: it turns idle once its row is selected in the dashboard, or in AGENTS while the sidebar has the keyboard (window focused). Done is not saved: it is per running paddock.
- Subagent task: running, waiting, done, or stopped.
- Compacting counts as running. Urgency (a space's dot, a tab's marker, `C-a a`): waiting, done, idle, running, unknown.
- Rows never sort by state, so none moves when its state changes: session rows follow their panes' spaces, tabs and splits, task rows their tree, external rows their labels (then keys). `C-a a` alone goes by urgency: most urgent first, row order within a state.

### Attention

- Waiting rows and agents get a strong highlight; done (bold) and idle ones a soft one. Tabs holding such sessions are highlighted and marked `●` too.
- Desktop notifications fire when a session or one of its subagents starts waiting and when a main agent goes idle (a subagent finishing never notifies), but not when that terminal is already focused. An external session notifies and gets its dot like any other, but `C-a a` skips it: there is nothing to jump to. `[notify] waiting = false` or `idle = false` turns off that kind (both default to `true`); only the notification goes, while states, highlights, markers, `C-a a` and the dashboard stay as they are.

### Preview

- The dashboard shows a live preview of the selected row. A subagent's task row shows its session's screen. An external session has no screen: its preview says `external session: no screen`.
- `I` enters interactive preview and types into that session; `Esc` leaves and is never sent to Claude; so does any Alt key, since `Esc` and a key read together arrive as one. To interrupt Claude, jump to the session.

### Actions

- **Close** (`x`): closes the focused pane, or in the dashboard the row's pane; its tab goes with its last pane and its space with its last tab. In the sidebar, `x` closes the selected space, or the selected agent's pane. Asks first if an agent is running or waiting there.
- **Fork** (`f`): runs `claude --resume <id> --fork-session` in a new tab of the same space, in the session's directory. Moving the fork into its own worktree is Claude's job (its `EnterWorktree` tool).
- A single subagent can only be stopped from inside its session.
- An external session can only be dismissed (`D`): `Enter` (dashboard, sidebar or a click) shows `external: open it in its own terminal`, and `x`, `f` and `I` are refused with a notice, so nothing paddock does reaches a pane for it.

### Mouse

- Click: focus a terminal, open a space or jump to an agent, switch tabs.
- Wheel: scroll a terminal's history.
- Drag: select text; releasing copies it.
- In copy mode the wheel scrolls the copy view; a click or drag leaves it first.
- Programs that ask for the mouse (vim, htop) receive it; hold Shift to select anyway.
- Drag the border between two splits: resize them, live; the sizes stay in tmux. It never selects text.
- Drag the sidebar's border: resize the sidebar.

### Keys

Prefix `C-a`, configurable; pressing it twice sends a literal `C-a`.

Every key paddock reads is a named action in one table per mode (`src/input/keymap/tables.rs`): after the prefix (`[keys.commands]`), with the sidebar focused (`[keys.sidebar]`), in the dashboard (`[keys.dashboard]`) and in copy mode (`[keys.copy]`). The same commands fire without the prefix on a direct chord (`[keys.direct]`, the commands' table with each command's default chords: `C-h/j/k/l` focus, `C-M-c` new tab, `C-\`/`C--` splits; cycling tabs has none, as `C-M-[` is two `Esc` outside the kitty protocol), whenever a terminal has the keyboard and no float shows (a float gets every key but the prefix); it never waits for a second key, and matches only as bound. The help overlay shows each command's chord after it in brackets, which keeps it within 80x24; to stay within it, a group of commands may share one cell (`ui::help::SHARED`: `< >` moving a tab, `HJKL` resizing a split, `{ }` the sidebar's width, `[ /` copy mode and search). Since `C-h` and `C-j` are Backspace and Enter to the terminal, a `[keys.direct]` not written at all gives a notice at start naming the control characters taken (`C-h`, `C-i`, `C-j`, `C-m`, `C-[`); written, even empty, the user chose them (`Keymap::configured` decides). Dispatch, the help overlay, the dashboard's key line and `paddock keys` (the defaults as TOML) are built from those tables, and a unit test checks that the key tables in [keys.md](keys.md) match them, so that page is where the default keys are listed. `config.toml` gives an action one key, a list, or `""` to unbind it; an action left out keeps its defaults.

One key grammar serves the prefix and the bindings (`src/input/keymap/key.rs`), normalised the way terminals report keys: Shift folded into characters, a Ctrl letter always lowercase, and the characters that share one control byte folded into one key: `C-_` and `C-7` are `C--`, `C-4` is `C-\`, `C-5` is `C-]`, `C-6` is `C-^` (the digits are what crossterm reports 0x1c-0x1f as without the kitty protocol). No other keys fold, so under kitty `C-/`, `C-3` and `C-2` stay keys of their own. Defaults avoid Alt (any terminal app), except the direct chord `C-M-c`, which gives no warning; `M-` keys the user binds are accepted with a warning, shown at start and printed again on leaving. As before keys were configurable, Shift does not matter after the prefix, and Ctrl and Shift do not matter in the sidebar and dashboard, unless a key is bound with them. Config errors stop paddock before it touches the screen, naming the file, section and action: an unknown action or section, a key that does not parse, a key listed twice for one action, one key bound to two actions in one section (defaults included), or the prefix key bound inside a section (it always starts a command). `[floats]` keys use the same grammar and fail the same way, and also when one is bound in `[keys.commands]` (the default `G` included); `width` and `height` are whole percents from 1 to 100.

Some keys are fixed on purpose: the prefix twice sends it; `Esc` always leaves typing into the dashboard preview and is never passed on, so no remap can trap you there; prompt editing (`Enter`, `Esc`, `Left`/`Right`, `Home`/`End`, `Backspace`/`Delete`, `C-u` (clear), `C-w` (delete word)), the finder's keys and the dashboard filter's (the same editing, `Up`/`Down`, `C-p`/`C-n` and the state letters in the finder), copy mode's search prompt (the same editing), the `y` that confirms a close or a worktree delete, and `j`/`k`/`Enter`/`Esc` in the worktree list.

**Copy mode** (`C-a [`, `[keys.commands] copy_mode`; `C-a /`, `search`, opens it with the search prompt): the terminal typing goes to (the float shown, else the focused pane) holds its output back (`Terminal::pause`, at most 8 MiB, past which it goes on by itself with a notice), so its view stays still while the program runs; leaving feeds what was held and returns to the live view. A cursor moves over the emulator's own history and screen with `[keys.copy]` (`h/j/k/l` and arrows, `w/b/e`, `0`/`$`, `g`/`G`, `C-u`/`C-d`, `C-b`/`C-f`; the moves are alacritty_terminal's vi motions), `v`/`V` select characters or whole lines with the emulator's own selection, and `y`/`Enter` copy it through the same clipboard path as dragging (a line selection without its last newline) and leave; `Esc`/`q` leave. `/` and `?` open a search prompt edited like the others: plain text over history and screen, wrapped rows read as one line, case-insensitive unless the query has an uppercase letter (`fuzzy::ignores_case`, the finder's rule); `Enter` jumps to the nearest match back up from the cursor for `/`, down for `?`, `n` the search's way and `N` the other, wrapping; every match on screen gets a yellow background, and no match gives a notice with the cursor kept. The bottom row of the terminal shows ` COPY  line N/M ` (and ` match i/n `) with as many `[keys.copy]` keys as fit, or the prompt; it moves to the top row while the cursor is on the bottom one. The copy keys are listed there and not in the help, which only fits 80x24 with copy mode's two commands by dropping its blank line and showing them in one cell. The prefix works (a command leaves copy mode first), except in the search prompt, which takes every key; direct chords do not. The wheel over the terminal scrolls the copy view; a click or drag leaves copy mode and acts as usual. Copy mode ends when its pane closes, leaves the screen (another tab, the float hidden) or is resized. A default `[keys.copy]` key that is the prefix (`C-b` under a `C-b` prefix) is left out rather than refused. Known gaps: no regex, no `ge`/`W`-style moves, no block selection, and the match list is not refreshed while frozen (nothing changes then).

## Tasks and worktrees

A task is a branch ([ADR 0004](adr/0004-task-is-a-branch.md)), and, after herdr, a git worktree is a space. paddock reads `git worktree list` and branch status, and creates, opens and deletes worktrees as spaces; it changes nothing else in git. Subagents working in parallel still need their own worktrees; one line in the user's CLAUDE.md asks Claude to use worktree isolation for branch work in subagents (those worktrees are Claude's, and paddock only reads them).

- **Where:** `[worktrees] directory` (default `~/.paddock/worktrees`, `~` expanded, absolute, and not home itself, or a config error). A new worktree goes to `<directory>/<repo>/<branch>`, slashes in the branch written `-`; `<repo>` is the main checkout's directory name.
- **New worktree** (`C-a W`, action `new_worktree`; `W` on a space or agent in the sidebar): the prompt popup (` New worktree `, empty, edited like the other prompts) asks for a branch. A name `git check-ref-format --branch` refuses, or one with `@{` (git would expand it), or a path that exists, is a notice. In the focused terminal's working tree (or the selected space's), paddock runs `git worktree add -b <branch> <path>`, or `git worktree add <path> <branch>` if the branch exists, then opens a space named `<repo>/<branch>` with its first tab in that path and shows it. git's error shows as a notice, its `fatal:`/`error:` lines first, on one line. If the space cannot be made, the worktree is removed again (and the branch, if it was made for it): nothing is half-created.
- **Open worktree** (`C-a O`, `open_worktree`; `o` on a space in the sidebar): the popup (` Open worktree `, 60 columns, a line per worktree: the space name it would get and its path) lists the repository's worktrees that no space is in; `j`/`k` (or arrows) move, `Enter` opens a space for the selected one (named as above; the main checkout `<repo>`), `Esc` or a click outside cancels. These keys are fixed, like prompt editing. Without any, a notice says every worktree has a space. (It is not the finder's list: the finder is built around a typed query and its own row kinds and targets, and this list has no query, so `j`/`k` move.)
- **Which spaces are worktree spaces:** a space whose directory (its first tab's first pane's, read when the key is pressed, not the sidebar's last read) is a linked worktree laid out as paddock makes them, exactly `<directory>/<repo>/<name>`, and not right inside its own main checkout. A space belongs to the worktree of its first tab's first pane; its other panes do not count. That directory is read one way everywhere (`worktree::space_dir`, `list-panes -s` with the first pane that is not a float's): by these keys, by the sidebar's background read and by `paddock worktree`; a space whose directory is gone is in no worktree. Only those are ever deleted. A space in a main checkout, or in a worktree elsewhere (such as Claude's own `.claude/worktrees/agent-*`), is not one: sidebar `x` closes it as before, and `delete_worktree` there is refused with a notice.
- **Delete worktree** (sidebar `x` on a worktree space, which no longer just closes it; action `delete_worktree`, unbound by default, on the current space): ` Delete worktree ` asks `delete <branch> and its worktree (ignored files too)? y/n` (a detached worktree is called by its directory's name); any key but `y` cancels, and nothing is deleted or closed. Then, if the worktree has uncommitted changes (untracked files count; if git cannot tell, it counts as changed), or commits checked out there are not in the base (a branch's or a detached HEAD's, as the dashboard's merged, or none of its own), a second question names every such risk: `feat/x has uncommitted changes and is not merged into main: remove the worktree anyway? (the branch is kept) y/n`, or `… delete anyway? y/n` without an unmerged branch. A long question wraps in a box at most 64 columns wide. `y` again goes on. paddock then closes the space (along with every other space in that worktree, asking first if an agent is running or waiting in any of them, as close does; if git does not answer in time for some space, nothing is deleted: `couldn't read every space in time: nothing deleted`), removes the worktree with `git worktree remove` (with its ignored files; `--force` only when the user confirmed uncommitted changes), and deletes the branch with `git branch -d` (never `-D`). Right before removing, what the user did not confirm is checked again: uncommitted changes, or commits not in the base (a detached HEAD's too), made after the question (by an agent, say) leave everything as it is, spaces included, with a notice. If removing fails after the space closed, the notice names the directory left (see Git below). If `branch -d` refuses, the branch is kept and a notice says so, with git's reason; that is not an error.
- **Sidebar:** each space's working tree is read with its directory (`git rev-parse --show-toplevel` and the first entry of `git worktree list`). A space in a linked worktree is listed under its repository's main-checkout space, one cell further in (dot, name and second line), in their order; when no space is in the main checkout, a dim header row with the repository's name comes first (it picks nothing). Selection, `Enter`, `x`, `f` and clicks work on every space row as before (`x` deleting a worktree space, as above). This grouping uses the background read, so it may lag a few seconds; the decisions `x` and `C-a O` make never do.
- **Dashboard:** unchanged; a session in a worktree space shows that space's name. A PR column stays later.
- **Git:** every call runs `git -C <dir>` with argv, never a shell, `--` before paths and branches where git takes it; paths come from paddock and branch names from the prompt (`check-ref-format` takes no `--`, so a name starting with `-` is refused first). Every git paddock runs goes through one helper with a timeout, then git is killed: reads (the sidebar's and the dashboard's, and those `C-a W`, `C-a O` and `x` make) wait at most 5 s and then count as failed; adding and removing a worktree and deleting a branch wait at most 60 s, and a notice says so. The limit covers git's output too: a process git leaves behind holding it (a hook's `cmd &`) counts as not finished. The check of what a delete would lose has 5 s in all, across its reads; past that it counts as every risk, so the second question still asks, saying the check could not finish (`couldn't check feat/x in time: delete anyway, discarding any changes? (the branch is kept) y/n`; for a detached worktree, `discarding any changes and commits`). If removing fails after the space closed, the notice gives git's reason first, then the directory left (`<reason> (git worktree remove …); space closed, ~/…/feat-x left`; without a space closed, as from `paddock worktree rm` on a worktree with none, just `<reason> (…); ~/…/feat-x left`), so a `fatal:`/`error:` line leads.
- **Spaces made outside paddock:** a running paddock attaches, as a space at the end of the sidebar, any session that appears on the hidden server (`%sessions-changed`, which every space's control client hears; a session already attached is skipped), so `paddock worktree new` or `tmux -L paddock new-session` show at once; the current space stays. A session that ends, whoever ends it, leaves as before (its client's `%exit`); if it was the last, paddock quits, as when you close the last space by hand.
- **Help:** with these keys the help no longer fit 80x24 with its first line, so the prefix line moved into its top border (`paddock keys: C-a, then a key (C-a again sends C-a to the terminal)`); the bottom border carries `[chord]: works without the prefix`.

### Worktree command

`paddock worktree` (ticket 25) does what `C-a W`, `C-a O` and `x` do, for agents and scripts. It calls the same code as the keys (`src/worktree.rs`: the layout, `is_ours`, which spaces a worktree holds, the risk check and its 5 s deadline, create-or-roll-back, re-check-then-remove; `git.rs` with its timeouts) and drives the hidden server through `Backend` (`PADDOCK_TMUX_SOCKET`, paddock's config, the clean environment), writing the config and starting the server when none runs. Each space starts at 80x24; a paddock that attaches it resizes it.

- **Subcommands:** `new <branch> [--no-space]`, `open <branch|path>`, `list`, `rm <branch|path> [--discard-changes] [--discard-commits]`; each takes `--json` and `--from <dir>` (the repository of `<dir>`, else of the current directory). A `<branch|path>` that is a directory (relative to `--from`, else to the current directory) names the worktree it is in; else it names the worktree where that branch is checked out. If it names one worktree as a path and another as a branch, it names neither: exit 1, naming both, so a full path must be given. `paddock --help` and `paddock worktree --help` (also `-h`, `help`) print to stdout and exit 0.
- **Output:** text by default (`new`, `open`, `rm`: the worktree's path; `open` on a worktree with a space says `<path> already has a space: <name>` on stderr, opens nothing and exits 0; `list`: one line per worktree with aligned columns path (home as `~`), branch or `(detached)`, `main`/`linked`, `ours`/`-`, space or `-`, `dirty`/`clean`, `merged`/`unmerged`, the branch's PR as `#123 open` or `-`, agent states or `-`). `--json` gives `{"path","branch","repo","space"}` for `new` and `open` (`space` is `null` with `--no-space`, and is the name tmux gave, which writes `.` and `:` as `_`), an array of `{"path","branch","main","ours","space","dirty","merged","pr","agents"}` for `list` (`pr` is `null` or `{"number","state","checks","review","url"}`: `state` `open`, `draft`, `merged` or `closed`; `checks` `passing`, `failing`, `pending` or `null`; `review` `approved`, `changes_requested`, `review_required` or `null`, GitHub's `reviewDecision` in snake case), and `{"path","branch","closed","branch_deleted"}` for `rm`. Keys keep this order. `merged` is `true` for the main checkout. `list` asks `gh` once per call for the repository (`github::pr_list` in its main checkout, on a thread while the rest is read, with the same 5 s limit; no cache, nothing logged, nothing on stderr); without `gh`, when it fails or is late, or with `[github] refresh_secs = 0` (then it is not run), every `pr` is `null` and the exit code is unchanged. Errors are one line on stderr (`paddock: …`); a notice (a branch kept) goes to stderr too, with exit 0. Nothing reads stdin or needs a TTY.
- **Exit codes:** 0 ok; 1 usage or config error (a bad branch name, a path that exists, not a repository, no such worktree, a config error); 2 git or backend error (git's `fatal:`/`error:` reason; tmux refusing a space, such as a taken name, which rolls the worktree back); 3 refused for a risk; 4 timeout (git, or `claude agents --json`, did not answer in time; nothing deleted).
- **Agent states** (`list`'s `agents`, `rm`'s busy check) come from where the app gets them: the hook event log of the running server (`<state>/events/<pid>.jsonl` for tmux, `<state>/events/native-<id>.jsonl` for the native server, see `sessions::log::path`) replayed, then `claude agents --json`, waited for at most 5 s. `list` leaves floats' panes out, as the sidebar does; `rm` counts them, since closing the space kills its floats too. Dismissed rows count: a dismissed Claude may still be running. For `rm`, a late `claude agents` is exit 4; for `list` the log's word stands.
- **`rm` checks**, cheapest first, each refusing with exit 3 and naming the risk: the main checkout; a worktree paddock did not make (`is_ours`, as `x`); the caller's current directory inside it (whole path parts, links resolved); the caller's terminal (`backend::hook_terminal`: `$PADDOCK_PANE` on the native backend, `$TMUX_PANE` on tmux, each believed only when its socket variable names paddock's socket, and only for the backend instance that runs now) in one of the spaces it would close or with its directory inside it; then the risk check (late: exit 4, before `claude agents` is asked), naming every risk not discarded (`feat/x has uncommitted changes (--discard-changes loses them) and has commits not in main (--discard-commits removes the worktree anyway; the branch is kept): nothing deleted`; a detached HEAD's commits are the only ones lost, so it says `has commits not in main on a detached HEAD (--discard-commits loses them)`); then an agent running or waiting in any pane, floats' included, of those spaces, or in any pane whose directory is inside it. Then, as `x` does after its questions, what was not both found and discarded is checked again right before anything closes (a flag consents only to a risk the check found: changes made after it are refused, never `--force`d), the spaces close, `git worktree remove` runs (`--force` only with `--discard-changes`), and `git branch -d` (never `-D`) keeps an unmerged branch with a notice.
- **Known limits:** `is_ours` goes by layout only, so a worktree made by hand at `<directory>/<repo>/<name>` counts as paddock's (as for `x`); an agent outside paddock's server (another terminal app) is not seen by the busy check, and only the re-check for changes protects its work; a `git worktree remove` that runs past its 60 s limit does so after the spaces closed, so that exit 4 comes with the spaces gone (`list` shows what is left); the command takes no lock against an open paddock, so an `x` and an `rm` at once can race (both re-check, so at worst one fails).
- **Plugin:** the repository is a Claude Code plugin marketplace (`.claude-plugin/marketplace.json`) with one plugin, `paddock` (`plugins/paddock/`): paddock's hooks (see Hooks), the skill `paddock-worktrees`, which Claude loads when work should go to another branch in parallel, and two user-only skills that run as `/paddock:worktree-new <branch>` and `/paddock:worktree-list`. The skills pre-approve only `list`, `new` and `open`; every `rm` asks the user. `tests/plugin.rs` checks the manifests and each skill's frontmatter in `cargo test`, and runs the hooks' commands through `sh -c` in a sandbox: silent without `paddock` on `PATH`, and one record per event with the plugin alone or with `hooks install`'s hooks too; a unit test in `src/hooks.rs` checks `hooks.json` against `EVENTS`; `claude plugin validate --strict .` and `claude plugin validate --strict plugins/paddock` check them in full.
  - *Gemini CLI and Antigravity CLI.* `gemini extensions install` takes a repository and a `--ref`, not a subdirectory, so the repository root is also a Gemini CLI extension: `gemini-extension.json` (`name` `paddock`, `version`, `description`; no `contextFileName`), `skills/paddock-worktrees/SKILL.md` and `commands/paddock/worktree-new.toml` and `worktree-list.toml` (`/paddock:worktree-new <branch>`, `/paddock:worktree-list`). agy has no format of its own to point at a subdirectory either; `agy plugin install <GitHub URL>` converts a Gemini extension into an agy plugin (`agy plugin validate .`, agy 1.4.5, says so; no install was run), which loads its skills; agy's validator warns that plugins do not load `commands/`, and an extension it converted here kept them unconverted, so agy is expected to get the skill alone (not checked with a real install). Neither carries hooks, nor a `GEMINI.md` or `AGENTS.md` (both agents would also read those as rules for whoever works on this repository): a `hooks/hooks.json` would record each Gemini or agy event twice beside `paddock hooks install`'s, as only Claude's plugin hooks step aside (`PADDOCK_HOOK_SOURCE`), and agy stages a converted extension's hooks too. For the same reason agy must not import the Claude plugin. Gemini reads only `name` and `description` from a skill's frontmatter and has no user-only skills, hence commands; the skill and the commands are copies of the Claude plugin's, kept equal by `tests/plugin.rs` (the skill's body and description; each command's prompt is the Claude skill's body with `$ARGUMENTS` as `{{args}}`). Skill bodies speak of agent sessions and coding agents, not of Claude. Only Claude Code has a pre-approval list (`allowed-tools`, without `rm`); Gemini CLI and agy rely on their own approval mode, so the skill says to ask the user before each `rm`, merged or not. The `worktree-new` command's branch is typed by the user: the prompt runs nothing unless it is one token of `A-Za-z0-9._/-` not starting with `-`, and then only `paddock worktree new '<branch>' --json`; Gemini still asks before its shell tool unless auto-approve is on.
  - *Versions.* A release bumps `version` in `plugins/paddock/.claude-plugin/plugin.json` and `gemini-extension.json` with `Cargo.toml`; `tests/plugin.rs` fails while either differs from the crate's version. `gemini extensions update` follows the default branch (`main`), which only releases reach.

## Facts checked for Gemini CLI (0.64.0, from its bundled source and docs)

- Hooks live in `settings.json` under `hooks`, in Claude's shape; `hooks.enabled`, `hooks.disabled` and `hooks.notifications` are settings, not events. A group without a matcher matches everything. `timeout` is in ms (default 60000). Hooks run through the shell, in the session's directory, with the CLI's environment (`$TMUX` and `$TMUX_PANE`, or the native backend's `$PADDOCK_PANE`, `$PADDOCK_SOCKET` and `$PADDOCK_INSTANCE`, included; only secret-looking variables are redacted, and only when redaction is turned on) plus `GEMINI_SESSION_ID` and the like. Stdin gets `session_id`, `transcript_path`, `cwd`, `hook_event_name`, `timestamp` and the event's fields; stdout, if any, is parsed as JSON.
- Order around a permission: `BeforeTool`, then `Notification` (`ToolPermission`, with `message` and `details`), then, once granted, the tool, then `AfterTool`. `BeforeAgent` fires once per prompt and `AfterAgent` once at its end; an Esc cancel (and a denied permission, which cancels the turn) fires neither `AfterAgent` nor `AfterTool`.
- `/clear` (also `/new`): `SessionEnd` (reason `clear`), a new session id, then `SessionStart` (source `clear`). Quitting sends `SessionEnd` (reason `exit`).
- Settings hooks run only in a trusted folder; folder trust is on by default.
- The settings file may hold comments (Gemini strips them).

## Risks

- Claude Code's transcript files, `.meta.json` and the `claude agents --json` fields are undocumented and may change. Hooks are the primary source; these only reconcile.
- The renderer is the largest piece of work, and encoding keys, mouse and paste for control mode is the hardest part of it. Spike 0a gates the build.
- One instance at a time is the price of having no daemon.
- A session ends for paddock on `SessionEnd` or when its terminal closes. An agent killed without `SessionEnd` (e.g. `kill -9`) keeps its row, in its last state, until its terminal closes or it is dismissed.
- Antigravity CLI is closed source and needs a sign-in: its hook payloads were shaped from its docs, not recorded, so the shape of `workspacePaths`, the hooks' environment (`$PADDOCK_PANE` or `$TMUX_PANE`, which places an event in its terminal) and whether an empty reply would do are unchecked. Its status reports were captured from a real 1.4.3 run (the sign-in screen and quitting only).
- Gemini CLI has no snapshot to catch what its hooks miss: after an Esc cancel or a denied permission its row stays running or waiting until the next prompt. Its payloads were read from 0.64's source, not recorded from live runs, and its hook API is young.
